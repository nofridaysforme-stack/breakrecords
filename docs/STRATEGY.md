# Implementation strategy: where we are

The plan is the End-to-End Implementation Strategy (Nov 7, 2026, PDF version): keep the typed API as the seam, replace the mock behind it one module at a time in the order money flows, and take each module live only after a pilot user completes the real task with it. Backend detail comes from the Platform Build Plan and the Splits and Percentage Spec.

## Decisions

| Topic | Decision | Source |
| --- | --- | --- |
| Database | Postgres on Supabase Pro (row-level security, point-in-time recovery) | Strategy PDF |
| Hosting | Next.js on Vercel; Railway only for long-running workers (Python statement parsers, audio); Inngest for workflows | Strategy PDF |
| Auth | Auth.js v5 email magic links with an invite allowlist and database sessions, as in the Trading Platform. Not Clerk (the strategy and build plan still list Clerk; Jana chose this on Nov 7) | Jana |
| Migrations | Plain SQL run by dbmate, as in the Trading Platform. Drizzle is used only as the Auth.js adapter | Trading Platform |
| Payouts | Trolley for royalty payouts and tax forms; Stripe only for subscription billing | Strategy PDF |
| Stage 0 gate measure | The API contract (`packages/contract`, every endpoint the UI calls), not a screen count. Pages may be added or removed later | Jana |
| Mock/live switch | On the server (`BR_LIVE_MODULES`), so partner keys never reach the browser | Stage 0 |

## Stages and gates

| Stage | Estimate | What goes live | Gate to move on |
| --- | --- | --- | --- |
| **0 Foundations** (now) | about 3 weeks | Contract freeze, Postgres on Supabase, auth, row-level security, staging, CI, module flags | Every endpoint in the contract runs on the live API in staging; cross-tenant reads fail |
| 1 Data in | about 4 weeks | Catalog and statement import, parsers, splits engine, read-only statements | 3 pilots' last 12 months reconcile to the cent |
| 2 Agreements | about 3 weeks | Splits editor live, Dropbox Sign, attorney templates | Every pilot track has a signed split totaling 100% |
| 3 Money out | about 4 weeks | Approvals live in production, Trolley payouts, tax forms, daily reconciliation | Real payouts to 3+ payees; zero differences for 2 periods |
| 4 Agents | about 6 weeks | Label Head plans; Royalty, Registration and Funding agents; evals | Evals pass; pilots accept plans; one prepared registration confirmed |
| 5 Releases | about 4 weeks | LabelGrid delivery, runbook live, pitch drafts, Stripe billing | A pilot single goes live on Spotify, delivered from the platform |
| 6 Paid beta | ongoing | Open signups, white-label tier, then Phase 2 marketing | Paying tenants renew; support load fits one person |

Stage 3 is the point of no return: attorney sign-off, insurance and a staging rehearsal come first. Staging runs every module live; production flips one module per gate.

## Stage 0 progress

### Done

- **Workspace:** `apps/web`, `packages/core` (money math, approval rules), `packages/contract` (Zod), `packages/db` (SQL migrations, tenant-scoped client).
- **Contract:** schemas for every read the UI makes (33 endpoints) and every write; checked at compile time (`contract-check.ts`) and over HTTP (`contract.spec.ts`, mock; `tests/live`, live).
- **Database:** tenants (licensee, label, artist), Auth.js tables, invite allowlist, memberships, approvals, decisions and an append-only audit log. Row-level security on every tenant table, with the app connecting as `br_app`, a role that owns nothing. 11 tests prove cross-tenant reads and writes fail (`packages/db/tests/rls.test.ts`).
- **Auth:** magic links (Resend in production, a test mailbox locally), invite-only, 30-day database sessions, a "Continue" step so link previews can't use up a link. `BR_AUTH=required` turns it on; live data is refused without it.
- **First live module: approvals.** With `BR_LIVE_MODULES=approvals`, the inbox, detail, Home cards, decisions, bulk approve, undo and in-app proposals read and write Postgres for the signed-in tenant, using the same rules as the mock (`packages/core/src/approvals.ts`), one writer per tenant at a time, every change in the audit log. Payees are refused.

- **Second live module: catalog.** With `catalog` in `BR_LIVE_MODULES`, the Catalog screens read the tenant's parties, songs (with writer shares in basis points), recordings, credits, releases, tracks, assets and registrations from Postgres. Metadata scores are computed from the data (`packages/core/src/metadata.ts`: twelve checks, rounded down) instead of stored, and the note says exactly what's missing. Genre and AI use edits save through `PATCH /api/catalog/recordings/{id}`, are audited, and rescore the recording. Records can't point across tenants (a database trigger refuses it), and payees can't read the catalog.
- **Third live module: registrations (Rights).** With `registrations` in `BR_LIVE_MODULES`, all three Rights tabs read Postgres. The registrations matrix lists every recording that is on a release or has a filing of its own (an unregistered release shows as a row of "Not started"; a demo that only shares its song stays out), with PRO and MLC read from the song and the rest from the recording. Unclaimed royalties are stored in cents with their source, the song or recording they're for, and a status from found to paid. Profile claims are stored per artist and service; "Prepare the rest" saves through `POST /api/rights/claims/prepare` in both modes and is audited. Preparing a claim on unclaimed money still goes through approvals.
- **Fourth live module: splits.** With `splits` in `BR_LIVE_MODULES`, the split tree and each node's versions come from Postgres. A version is a rule with a status: draft, sent for signatures, in effect, superseded. The rules live in `packages/core/src/splitVersions.ts` and are backed by the database: a version can only leave draft when net profit totals exactly 100%, a node has at most one open and one in-effect version, and the last signature puts a version in effect and supersedes the old one (a database trigger, so it happens the same way whoever signs last). Draft edits, sending and signing go through `PUT /api/splits/{node}/draft`, `POST .../send` and `POST .../sign` in both modes, and the editor and the payee portal no longer keep the split in the browser. Live, a payee's login is linked to their party: they see only the versions they're on (never drafts), the names of their co-signers, and can sign only their own line; the label's owner and team sign only for the label. The market-range note is computed from the producer points.
- **Fifth live module: statements.** With `statements` in `BR_LIVE_MODULES`, Royalties, the statements list, statement detail and the portal's statements read Postgres. What a source reports is stored as an income statement with its lines, as sent (typos included), in cents. A statement whose lines don't add up to its printed total, to the cent, never commits (a deferred database check), and matching a line can only change what it points at, never the money. Royalties are computed from the lines: totals by source and artist, matched counts, the change on the period before, tracks that earned $0.00, and unclaimed money from Rights. A reported ISRC one keystroke away from exactly one recording is suggested as a typo (`packages/core/src/statements.ts`); a person matches it through `POST /api/money/royalties/match` in both modes, and the match is audited. Payee statements are stored as issued and never edited (the app can't update them; a correction is a new statement), each must end on its net, and the server checks each one again before serving it. A payee reads only their own statements and none of the label's income.
- **Sixth live module: payouts.** With `payouts` in `BR_LIVE_MODULES`, Payouts, Recoupment and the payee portal read Postgres. A batch is a set of payout lines (included, held, carried forward under the minimum, paid, failed), and its total, payee count and note are computed from them. Money only leaves through an approval: the database refuses to mark a batch sent unless its approval has an approved decision, marks that approval executed (ending undo), and freezes the batch and its lines once sent. History from before the platform is marked `imported`, a column the app can't write. Nothing in the app sends money yet; that is Trolley, Stage 3. Asking a payee for a tax form or new bank details is recorded through `POST /api/money/payouts/requests` (one open request of each kind per payee) and audited; the provider will send it. Recoupment is a ledger per release: the advance, each cost's recoupable share, and what each period took back, with the month it was recouped worked out from the entries (`packages/core/src/payouts.ts`). Costs are added through `POST /api/money/recoupment/costs` and audited. The portal is built from the payee's own rows: earned (opening balance plus statements), paid, the next payment and how it was worked out, tax form, the last four digits of the bank account, splits and songs, and what a new split version changes for them. A payee only ever gets their own portal; payee ids are party slugs (`marco-dela`) in both modes.
- **Seventh live module: releases.** With `releases` in `BR_LIVE_MODULES`, the releases list, each runbook and Budgets read Postgres. A runbook is phases and tasks. A phase is on a fixed date ("Now") or a number of days from the release date ("8 weeks out" is -56), so a new release date moves every relative phase. Phase and release status are worked out from the tasks and today's date (`packages/core/src/runbook.ts`): blocked when a gate is still locked after its phase starts, at risk when over budget or a decision has waited more than two weeks. "What blocks delivery" is the unfinished tasks that carry a reason, so a blocker goes away when its task is done. Assets, credits and the five registrations come from the live catalog; budget and spent from the release's budget lines. A date change is still a plan to approve: once it is approved, the server serves the new date to everyone, and undo puts it back. Payees and other labels see no runbooks.
- **Eighth live module: contracts.** With `contracts` in `BR_LIVE_MODULES`, Contracts and the template pages read Postgres. An agreement comes from one of the label's templates (with how many edits) or from a third party (and whether Legal reviewed it). Its counterparties sign, a band as its members, and the label signs by approving it, so an agreement with an open approval waits on you and its next date is the approval's due date. A split sheet is the song's writer split: its parties, "75 / 25" terms and signatures come from the writer shares, so there is one record of who wrote what. Signatures, key dates and the summary are worked out (`packages/core/src/contracts.ts`). Sending a contract for review is saved through `POST /api/contracts/reviews` (PDF or Word, by name until uploads exist) and audited; Legal Agent never signs or replies. Drafting from a template was already a proposal in approvals. Payees and other labels see no contracts.
- **Ninth live module: roster.** With `roster` in `BR_LIVE_MODULES`, the Roster reads Postgres. The only new table says who is on the roster and in what role; each card is read from tables other modules keep: genre and releases from the catalog, the agreement and its signatures from contracts, the latest period's matched income from statement lines, and the one open item, most urgent first, from the agreement's approval, the tax forms of the artist and their co-writers, and the next release (`packages/core/src/roster.ts`). Payees and other labels see no roster.
- **Tenth live module: funding.** With `funding` in `BR_LIVE_MODULES`, Funding (all three tabs) and the offer comparison read Postgres. Grants and offers are stored with their real terms: cash, what an advance repays, the share given up, the album a sale takes. Every card is worked out from those terms with the same offer math the comparison uses (`packages/core/src/funding.ts`), so "About $960, 14 months" and the comparison always agree, and the comparison page now reads the API instead of the sample file. The comparison's starting assumptions are stored per label (Finance Agent's estimate; from 12 months of statements in Stage 1). Dismissing a card, declining the sale (both undoable) and questions for the offerers are saved and audited; Finance Agent drafts every reply for the label to send. Accepting the advance was already an approval. Payees and other labels see no funding.
- **Eleventh live module: activity.** With `activity` in `BR_LIVE_MODULES`, Departments and the activity log read Postgres. Each department stores its agent, autonomy level, spend cap and the person it's handed to; whether "Act within limits" is allowed at all is a platform rule the database enforces (Legal, Finance, Publishing and Rights always wait for you), and the app can change only the autonomy level and the person, who must be on the label's team. The team is the label's real members with their titles. The activity log is what agents reported (append-only, with inputs, reasoning and output) merged with the audit log, so every approval, match, request and edit people make in the app appears there without extra code (`packages/core/src/activity.ts`). Changing a department is saved through `PATCH /api/departments/{id}` and audited. Payees and other labels see none of it.
- **Twelfth live module: settings.** With `settings` in `BR_LIVE_MODULES`, Settings and White label read Postgres. Label settings, approval routing (signatures, filings and public posts always need a person; the database refuses a cap on them) and integrations are stored per label, and the minimum payout is read from payouts so there is one number. Connecting an integration needs that partner's account, so live mode says which stage brings it rather than pretending to connect. The white-label theme belongs to the licensee: its labels read it, only the licensee's owners publish it, the database refuses anything but five valid colors, and the server checks every text pair against WCAG AA before saving. Publishing is audited. The licensee's label list counts each label's real roster.
- **Every module now has a live backend.** With all twelve in `BR_LIVE_MODULES`, every endpoint in the contract is served from Postgres for the signed-in tenant, and the live end-to-end suite runs with all of them on. What stands between this and the Stage 0 gate is staging (accounts) and CI.
- **Home and ⌘K on live data.** Home's money row is read from the same tables as the money screens: the latest period's income, what's owed in batches waiting on you, what the period recouped, unclaimed money, and a plain forecast (the recent monthly average for 90 days, less payouts due), each with a note saying what it covers. ⌘K searches through `GET /api/search`, whose index is built from the same reads the screens use, so live it finds the label's own data and nothing of another label's; the bar shows built-in results at once and swaps in the server's.
- **Published themes apply to everyone.** Once a licensee publishes its theme, every page of its labels' app and their payees' portal is served with it (the variables are written on the server from validated colors). The portal says which label pays you.
- **Onboarding answers are saved on the server** as you go (`GET`/`PUT /api/onboarding`), so they survive reloads and other devices. Finishing sets the label up from them: its profile and country, and every active department's autonomy, never past what the department allows. The tab's own copy wins over the server's while you're answering.
- **Everyone runs their own workspace.** Artists, bands, labels and label services each get a workspace with every tool (catalog, rights, documents, releases, contracts, money, roster, settings). Owners invite co-owners and team members into their workspace, or an artist or other payee. An invited payee's first sign-in makes their own workspace (they set it up as any of the four kinds, and own it); the inviting label becomes a connection under Labels I work with, where they see only what their deal covers (their statements, splits, payouts and tax form, the payee portal). The label never sees inside their workspace. Invitations are emailed (Resend); if the email fails the invitation still stands. The switcher lists the workspaces you run or work in, and starts a new one of your own (migration `own_workspaces`). A licensee's owners act as owners in its labels.
- **CI.** `.github/workflows/ci.yml` runs on every pull request and push to `main`: lint (types and copy rules), unit and row-level security tests against Postgres 16, the browser suite on sample data (screens uploaded for side-by-side review), and the browser suite with every module live. `.github/scripts/test-db.sh` builds the test database the same way as below.
- **Ready for staging.** `docs/STAGING.md` is the runbook. The Staging workflow (run by hand) migrates, seeds and runs the Stage 0 gate (`apps/web/scripts/stage0-gate.ts`): every contract endpoint live, other labels and payees refused, and nothing in the database reachable except through the app role. The `lockdown` migration takes every table and function away from Supabase's API roles and from PUBLIC. The database client turns off prepared statements behind Supabase's transaction pooler.
- **Sign-up with invite codes.** Indie SRVCS staff (`platform_admins`, seeded from `STAGING_OWNER_EMAILS`) make invite codes on the Invite codes page: a note, a number of uses, an expiry; only a hash is stored and the code is shown once. Someone with a code signs up at `/sign-up` with their email; their first sign-in creates their own workspace (they own it, with every workspace's defaults: departments, approval routing, integrations) and takes them through onboarding before anything else. Finishing onboarding names the workspace and sets its kind from the profile: solo artists and bands get an artist workspace ("personal label" in the sidebar and copy, "team" for people, no Roster); small and growing labels and label services get a label. A real workspace's setup starts blank (never the sample label) and doesn't claim a distributor connection or catalog import that isn't built yet. **Bands** add bandmates' emails at the name step; they become co-owners and sign in with their own email. **Label services** become a parent workspace (licensee): a Clients page adds each client (an artist or a label) as its own workspace, separate from every other client, which the services team opens from the list or the label switcher and works in as owners, inviting the artist from its Team settings. Service fees and client statements come later.
- **Prepared documents (module `documents`).** Rights → Documents prepares split sheets, registration packets (PRO and The MLC for a song, SoundExchange for a recording), copyright worksheets (song or recording) and label copy (release), for every artist on the label, from the catalog's own facts (`packages/core/src/documents.ts`). What each organization asks for, with sources, is in `docs/RIGHTS_REQUIREMENTS.md`. A missing fact is never guessed: it's listed as a gap ("to fix" or "to check") on the document and saved with it. Each version is a PDF (plus a CSV where organizations take a spreadsheet) in private storage (Supabase Storage over its S3 interface; a folder locally) and a row that is never changed or deleted. Downloads check, in the database, that the document is the label's. Writers' PROs, IPIs and roles, publishers, legal names and the master owner are new catalog facts (migration `documents`). Optional AI review (Claude) suggests problems and next steps beside a document, never changing it; it needs the platform switch (`BR_AI=on` and a key) and the label's owner to turn it on, and addresses and emails aren't sent. The platform prepares; a person submits.
- **ISRCs and UPCs.** A recording's ISRC is typed in its Edit dialog and a release's UPC beside it on Releases; both are checked (an ISRC's shape, a UPC's check digit) and must be unused across the platform. Owners save their ISRC prefix (country and registrant code, e.g. US-NL1) and GS1 company prefix in Settings › Profile; then "Assign" gives a recording the next ISRC for this year (00001 restarts each January) or a release the next UPC with its check digit, skipping any code already in use (migration `codes`, rules in `packages/core/src/codes.ts`). Imported codes are kept as sent.
- **Invitations by type.** Owners invite a co-owner, a team member, or an artist or payee. A payee is either someone already in the workspace or someone new by name, who is added as a payee when invited.
- **Approval checks (precondition engine).** Every approval card is checked against hard rules before Approve turns on (`packages/core/src/checks.ts`). Each rule has an id (ROY-01, PUB-03, FUN-03...), the approval types it applies to, a severity and a fix link. A failed **Block** rule keeps Approve off and puts the card under "Can't approve yet" at the top of Approvals; a failed **Warn** rule needs a typed reason, kept with the decision. A rule whose facts aren't recorded anywhere yet says "Can't check yet" and never blocks. The rules read the label's own tables (payout lines, splits, agreements, tax forms, income, releases, writers, the grant's deadline and an `audit_flags` table), never what the card says about itself, and run when a card is shown (`GET /api/approvals/checks`) and again on the server inside the approve transaction, so a refusal holds whatever the screen shows. Bulk approve refuses any card with a failed check. Every decision is logged with each rule's result and the inputs it read. Live checks use the real date; sample data keeps its fixed date, and its four cards fail the same rules as the live seed (`apps/web/src/data/checkFacts.ts`). Tests of the approve flow on sample data turn checks off with the `br_checks=off` cookie (sample data only). Rules in this first set: ROY-01 to ROY-09, PUB-01 to PUB-06, LEG-06, FUN-01 to FUN-03. Later: the other agents' rules, and tasks for the agent that owns a missing fact.
- **Data integrity (step 2 of the build list).** The sample label now tells a consistent story, and the checks pass on it except where a real problem remains. Glasshouse is the upcoming single (Mar 5, 2027), so it earns nothing yet: October's income, statements, payouts and the "recouped in October" all belong to Velvet Hours (its own split, v1, same deal). Low Light isn't released, so it earns nothing. Every paid person is covered by a signed split or agreement (band members through the band agreement, Ines Pardo through a mix engineer agreement). Every payout line matches its issued statement (ROY-06 now checks amounts against statements, which work out each share after costs). The MLC filing covers Velvet Hours, Night Bus and Static Hymn, all with signed split sheets and full writer details; Glasshouse follows once Marco signs. The Night Bus stream spike is resolved (it stays in the log). What still blocks: the grant, whose deadline was last checked over 7 days ago (FUN-03). The broken version of this data lives in the tests (`packages/core/tests/checks.test.ts`, and the live test that breaks the seed on purpose). Also: tax forms as the IRS defines them (a W-9 never expires; a W-8 lasts to the end of the third year after signing; treaty country, article and rate; withholding on each payout line; migration `tax_forms`), grant applications are Filings, the runbook marks code tasks done when the codes exist (MET-02), the producer template, draft and statements all pay points from the first dollar, a Splits index, the Q4 artist run, and the real date on Home in live mode. Home and Recoupment already read one ledger ($4,000 recouped). Not yet: funding offers projected from each asset's real income history (FUN-04), which needs the offers re-priced against the new income.
- **Onboarding that tells the truth (step 3).** The profile sets a starting point, never what's switched on: cards say what each profile "Starts with", and every tool stays in every workspace. Any top-level workspace can add clients (a client workspace can't have clients of its own), so Clients is in every sidebar, first for label services (migration `onboarding`). The PRO step became a Songwriting step that sets who owns or administers the songs (self-published, a publisher, we publish, we administer, writers handle their own); it's saved as `label_settings.publishing_mode` and rule PUB-02 uses it (filing as publisher fails when writers handle their own or a publisher does; we publish or administer can't be checked until publishing agreements are tracked). Setup saves the chosen autonomy as the default, and re-running it changes only departments still on the old default: any set by hand keep their level, and Finish says so. Finish lists only what happened (a distributor or catalog is "chosen", never "connected" or "imported"). Settings shows the saved default and songwriting choice, and its link reads "Change how Indie SRVCS is set up for you".
- **Publishing module (step 4).** Agreements now say what kind they are (`agreements.kind`: publishing, co-publishing, administration, and the existing kinds), with territory (worldwide, or minus a foreign sub-publisher's territory), term dates, admin fee and the label's publisher share (migration `publishing`). New templates: Publishing, Co-publishing and Administration. Rule PUB-02 now checks real agreements: with "we publish", each writer on a filing needs a signed, current publishing or co-publishing agreement; with "we administer", an admin agreement also counts; a writer marked as handling their own publishing (`parties.publishing_mode`) is never filed for. The sample label administers The Low Hours' and Kesi's songs, so the MLC filing passes. Not yet: an in-app way to draft these agreements from the templates (they're seeded or added by staff), a screen to set a writer's own publishing mode, RGT-02 (no copyright filing card exists yet), and statements for publishing income after the admin fee.
- **Agent rules for the cards that exist (step 5).** Signatures: LEG-01 warns when terms differ from the playbook (deciding every flagged term on the card is the reason, kept in the log), LEG-02 warns when the royalty base differs from the template, LEG-03 blocks a counterparty who isn't on the roster or the team, LEG-04 warns when points fall outside the playbook range; LEG-05 (attorney review) can't be checked yet. Release date plans: REL-01 blocks when the editorial pitch would land under 7 days before release and warns under 21, REL-02 blocks when spending is over budget, REL-03 checks every gate moves with the date. Funding offers: FUN-04 blocks accepting when the comparison's assumed income is more than 25% off the last 12 months of statements, annualized (the sample's $13,200 against about $158,000 a year, so the demo advance is blocked until the assumption is fixed); FUN-05 (artists agree first) can't be checked yet. The release runbook's pitch now sits in "4 weeks out". Approve stays off for the moment the checks take to load. Not yet, because the cards don't exist: DIS, MET, RGT, AUD, ROS, FIN, FUN-06 (sale confirmation) and AUD-03 (a second approval for owner invites).
- **Tax compliance (step 6a, P1 #3).** Withholding is worked out from each payee's form (`packages/core/src/tax.ts`): none on a W-9 unless the IRS has asked for backup withholding, 30% on a W-8 or its recorded treaty rate, and for a missing or expired form the workspace's choice on Payouts: hold the payout (default) or pay with 24% backup withholding (`payout_policies.missing_form_policy`). ROY-02 and ROY-03 follow that choice. A payee certifies their own W-9, W-8BEN or W-8BEN-E in the portal (`app_submit_tax_form`, payee only, closes any open request); only the last 4 digits of a taxpayer number are stored. Inviting a payee with no form opens a tax form request (ROS-02). Money › Payouts › Year-end forms totals payments sent in a year into 1099-MISC (US, $10 or more in royalties) and 1042-S (outside the US) rows; preparing them makes an approval card checked by TAX-01 (everyone paid has a form, block) and TAX-02 (taxpayer numbers confirmed, warn). Only after approval can the CSV be downloaded and the year marked filed, which ends undo (`tax_filings`, migration `tax_compliance`). Nothing is e-filed and no full taxpayer number is kept: that waits for the payout provider (Stage 3). Not yet: applying withholding to a batch's lines when it is sent (no batch is sent from the app until the provider), state forms, and sample-data invites opening a request.
- **Reserves and holds (step 6b, P1 #4).** Flagging a recording (Money › Payouts › Reserves, or the Audit Agent) opens a reserve: each unpaid payout line holds its share of that recording's income, pro rata to what the recording earned of its release in the month (`packages/core/src/reserves.ts`, `app_reserve_holds()`, `payout_lines.source_release_id`). Payouts shows what each batch holds, statements and the payee portal show the held part, and Home's Needs you lists flags waiting on a decision (AUD-02). ROY-07 passes once a flag's income is held. Resolving: real listeners proposes a release approval card, and the money stays held until it is approved; artificial streams forfeits it. A decided reserve never changes and nothing is deleted (migration `reserves`). Not yet: clawing forfeited money back from the distributor, and paying released money that was held from a batch already sent (no batch is sent from the app until the payout provider).
- **Your own music and splits.** Catalog › Add a release adds a release (single, EP or album) with its artist (someone in the workspace, or a new person or band) and its tracks in order, each with an ISRC if it has one (checked, never reused). Splits › Create a split makes a release's first split as a draft: the workspace is the label, the release's artist is the artist, plus an optional producer (points off the top) and featured artist (a cut of the artist share), using the same net-profit deal and roles as every other split. The draft can be changed until it's sent; then each person signs their own line (the owner and team sign for the label; "I am the artist" links a solo artist's login so they sign that line too; anyone else is invited by email and signs in their portal), and the last signature puts it in effect, after which it reads like any other split. New people get a payee record so they can be paid and invited. Splits and Catalog say what to do when they're empty. A split node points at its release (`split_nodes.release_id`, one per release; migration `split_releases`, with `app_link_me_to_party`). Not yet: splits with more than one artist or producer, song (publishing) splits from here, editing or removing a release, and starting a new version of a split that's in effect from these screens.

## Run live locally

```bash
# once: create the roles and databases (local Postgres 16)
sudo -u postgres psql -c "CREATE ROLE br_owner LOGIN PASSWORD 'br_owner_local' CREATEROLE"
sudo -u postgres psql -c "CREATE DATABASE breakrecords_dev OWNER br_owner"
MIGRATION_DATABASE_URL=postgres://br_owner:br_owner_local@localhost/breakrecords_dev?sslmode=disable pnpm --filter @breakrecords/db migrate
sudo -u postgres psql -c "ALTER ROLE br_app LOGIN PASSWORD 'br_app_local'"
SEED_DATABASE_URL=postgres://br_owner:br_owner_local@localhost/breakrecords_dev BR_ALLOW_SEED=1 pnpm --filter @breakrecords/web db:seed
```

Then start the app with the variables in `.env.example` (`BR_AUTH=required`, `BR_LIVE_MODULES` with all twelve modules, `AUTH_TEST_MAILBOX` set) and sign in as `jana@northline.example` (or `e2e-payee@northline.example`, Marco Dela, for the payee portal, or `e2e-licensee@harbor.example` to publish Harbor Sound's theme); the link is written to the mailbox folder.

Tests: `TEST_DATABASE_URL` (owner) and `TEST_APP_DATABASE_URL` (`br_app`) on a migrated test database, then `pnpm --filter @breakrecords/db test` (row-level security) and `pnpm --filter @breakrecords/web exec playwright test -c playwright.live.config.ts` (live end to end).
